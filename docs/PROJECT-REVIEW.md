# Project review — 7 October 2026

## Assessment

Pitch to Glory is a substantial browser-first football career game, with implementations covering all ten web milestones. Its strongest assets are the deterministic engine, explicit country rules, defensive save architecture, original procedural artwork, and the connection between matches and a long personal career. The highest-value next step is a focused hardening and playability pass before the Android milestone.

The product serves players who want to make football decisions and build a personal story without controlling a player in real time or managing an entire club. Desktop provides the richer information layout; mobile needs a complete, faster-to-read decision flow. Transparency, the rival, Chronicle, persistent world, and child careers are the clearest distinguishing features. Improvements should make those features interact more convincingly rather than add more disconnected management systems.

This review covers the current working tree, including the existing uncommitted match-motion changes. No implementation files were changed. Sources include AGENTS.md, architecture and milestone documentation, engine/model code, persistence/store/workers, route and screen code, CI and audit scripts, and hands-on production-browser inspection of career creation, the hub, briefing, and a live key moment at desktop and 390 px phone width.

## What is working well

- **Architecture:** simulation depends on serializable domain types, with browser APIs excluded from the engine. Heavy world simulation, validation and persistence have worker boundaries. The same simulation code can run headlessly.
- **Reproducibility:** saved RNG state and fixture-specific seeds support replay and statistical balancing. Country rules have versions and fingerprints so later code does not silently replace saved rules.
- **Save safety:** three slots, ownership and revision checks, durable weekly acknowledgements, isolated damaged slots, lazy migrations, and export/import are much stronger than a simple local-storage save.
- **Delivery:** route splitting, deferred renderer/audio/storage, production security headers, offline precaching, update handling, bundle checks and three-browser CI are already in place.
- **Visual identity:** forest green, warm neutral surfaces, gold rewards, Inter and Bebas Neue, readable cards, and consistent SVG crests/avatars give the game a recognizable football identity. Keep this direction.
- **Accessibility foundation:** keyboard decisions, labelled controls, route-based dialogs, reduced motion, simulation-only presentation, theme support and a populated-career axe sweep provide useful coverage.
- **Scope discipline:** the deliberate deviations from football rules and the simplified international/awards scope are recorded. Treat those as product choices to reassess, rather than undocumented implementation promises.

## Design and interaction improvements

The visual style is cohesive; the main problem is information hierarchy during play.

1. **Keep pitch context visible at key moments.** `src/screens/Match.tsx:321` focuses the first choice with default scrolling. On the inspected phone layout the canvas ended entirely above the viewport while the choices were visible. Desktop also scrolled into the decision area, cutting off much of the pitch. Use deliberate focus/scroll management, a compact situation preview beside the choices, and a layout that keeps score, pitch context and the active decision together. Preserve keyboard focus and screen-reader announcements.
2. **Make the mobile tutorial occupy space instead of covering controls.** `src/ui/Tutorial.tsx:143` uses a fixed card; on the first key moment it overlapped the choice area. Prefer an inline instruction panel, or reserve space for a sheet with a collapse control. Check action steps at large text sizes and short viewport heights.
3. **Simplify career navigation.** The global shell exposes eight destinations, and the career has seventeen more links. The mobile career row horizontally scrolls across all groups. Give active careers a focused navigation hierarchy: Overview, Player, Club, Life and History, with a More menu for secondary destinations. Move gallery/edit tools out of the main play path. Make hidden groups discoverable without requiring a long sideways search.
4. **Prioritize the next action on the hub.** The next-match hero and portrait are strong, but thirteen sections create a long dashboard. Give urgent decisions, injury recovery, expiring offers and unspent points priority; compress inactive summaries and let players expand or pin secondary information. The main action should be readily visible on a phone.
5. **Improve the week-to-week rhythm.** Add a career agenda combining fixtures, training, recovery, press and offer deadlines. Existing world fixture browsing does not provide a dedicated personal calendar. Show what advancing the week will resolve and offer a short digest afterwards.
6. **Compress decision copy while keeping explanations available.** Four expanded cards take a large amount of vertical space. Keep action, success chance and likely consequence immediately visible, with attribute breakdowns in the existing disclosure. Help players compare expected outcomes, not only headline success percentages.
7. **Make long lists and histories easier to use.** Inbox and history views can grow significantly. Add filters, date/season grouping, pagination or windowing where measured rendering cost justifies it. Preserve keyboard access and URL state. This follows the fetched [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md).

These are observations and design recommendations, not claims that the automated accessibility sweep failed. Absence of overflow or axe violations does not establish that a game moment is easy to understand.

## Engineering and release improvements

- **Make a finalized fixture result the shared authority.** Report, career record, world totals, bonuses, objectives, awards and Moments should agree on who played and what happened. Add cross-system invariants around that boundary, especially extra time and transfers.
- **Test long national careers and multiple generations.** A deterministic soak should cover many seasons, retirement, child careers, loans/transfers, migration and export/import. Measure payload growth and checkpoint latency against the 128 MiB import limit. Preserve historical identity while designing any archive compaction; do not silently drop people or milestones.
- **Audit populated play states.** `scripts/audit.mjs` currently visits entry routes without loading a career; the axe sweep uses a smaller legacy world. Add national-career scenarios, large inbox/history lists, a live renderer and a late-career save. Measure input latency, frame pacing, save pauses and memory alongside Lighthouse. Run performance measurements without concurrent simulation/browser workloads.
- **Promote performance to a release gate.** `.github/workflows/ci.yml` runs build budgets and browser journeys but not the configured Lighthouse audit. Use a scheduled or release job with stored artifacts and controlled hardware conditions.
- **Test an actual two-build PWA update.** Cover an old active career receiving an update, safely checkpointing, reloading, and continuing offline. Mocked update-manager tests alone do not establish the complete deployment/cache transition.
- **Complete physical-device acceptance before Android.** Verify Safari on macOS/iOS, IndexedDB storage pressure, install/offline behavior, audio unlock, background/resume, touch controls and sustained rendering on a mid-range phone.
- **Keep architecture summaries current.** The opening of ARCHITECTURE.md still frames later systems as typed contracts; later sections and source code have implemented them. Separate historical milestone notes from the current design and update test/bundle numbers only when measured.

## Recommended order

1. Correct result/statistics/award/legacy accounting, transient report state, wizard restoration and domain-dependent release tests.
2. Rework key-moment visibility, mobile onboarding, career navigation and the hub's next-action hierarchy.
3. Add long-career invariants and populated-world performance/device acceptance.
4. Connect formations, position learning and coaching feedback; add one persistent story arc.
5. Proceed to Android using the existing platform boundary after the web experience clears those checks.
